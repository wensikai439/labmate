# 提示流程

使用时填写方括号中的输入，并附相关源码片段与原始记录。模板里的文件名和字段名取自 LabMate；用于其他工程时，先按下表替换为对应模块，保留判断步骤与验收条件。先让助手给出结构和证据判断，人工核对后再实施修改；验证结果按执行日期和环境记录。

|技能|复用时替换的内容|保留的判断方法|
|---|---|---|
|S1|设备协议、命令、通道与完成查询方式|设置前状态、执行完成、错误查询、实际回读|
|S2|设备清单、调度器、数据年龄与界面字段|单台读数及时更新，整轮完成统一计时|
|S3|模型名称、任务类型、状态字段与资源阈值|资源取得与释放配对，异常后恢复|
|S4|实验或任务标识、作业状态、证据字段|按任务归属引用结果，隔离迟到响应|
|S5|后台运行器、进程标识、就绪日志与停止信号|确认本次进程就绪，重连与停止分开处理|

LabMate 的实际改动和已验证效果见 README.md 与 collaboration.md。其他工程的效果由替换后的源码和测试确定。

## 输入字段如何对应到其他工程

| 技能 | LabMate 中的含义 | 迁移时需要确定 |
| --- | --- | --- |
| S1 | 设备标识、通道、写入/完成查询/错误查询/参数回读 | 新协议对应的完成信号、错误含义和回读单位；不能直接照搬 SCPI 命令或等待时长 |
| S2 | `round_revision` 为整轮编号，`round_age` 为距整轮完成的时间；单台年龄用于 stale | 全部参与设备、整轮完成边界、单台过期阈值，以及事件通知机制；颜色可按新界面调整 |
| S3 | `active` 为实际引擎，`desired` 为期望引擎，`ready`/`switching` 为就绪/切换状态，`resource_busy`/`guide_busy` 为占用标志 | 各任务的资源所有者、峰值、锁与释放方式；6 秒录音上限是本项目历史设置，其他设备须测量后确定 |
| S4 | `workflow.run_id` 为本轮标识，`job.workflow_run` 为作业归属，`summary.id` 为异步写回标识 | 用项目实际的批次 ID、作业 ID 和写回令牌对应；明确成功状态、验证标志及单位，标识缺失时先补记录 |
| S5 | 当前 PID/启动段识别本次进程，ready/重连/退出日志区分连接状态 | 替换后台运行器、服务状态、停止信号和日志格式；DS 名称与 COM15 端口不构成复用前提 |

以下短例来自归档数据或已有测试，用于展示输入怎样形成判断与验收条件。测试中的时间、PID 和测量值为模拟输入，实机示例另标日期。

## S1 仪器命令完成与参数回读

~~~text
任务：分析连续 SCPI 配置的回读不符。
设备与固件：[IDN 原文]；通道：[目标通道]。
目标设置：[仅用户要求的字段]。
初始设置及输出状态：[逐项值]。
原始日志：[保留 WRITE、REPLY、等待、错误队列、返回码顺序]。
相关源码：[命令发送、等待、参数核对和失败处理函数]。

请先：
1. 列出语音文本、结构化目标、执行命令、实际回读各自能证明的事实。
2. 从第一个不符点构造最小失败序列；区分发送前拒绝和发送后失败。
3. 检查模式/波形切换是否逐步等待完成、查询错误并核对结果。
4. 给出最小改动，保留通道隔离和原输出状态处理；失败后停止后续设置。
5. 给出模拟回归、现场测试前状态记录及测试后恢复对照表。
当前阶段只分析日志和离线副本。现场验证按已有授权和设备状态另行安排。
~~~

验收表至少包含：请求字段、切换后回读、最终回读、错误队列、返回码、初始/最终输出状态、未操作通道对照。遇到 SYST:ERR?=0 而波形不符，仍判为配置失败。可按 [检查入口](checks.md#commands) 核验本项目旧失败与修复案例。

**S1 已填示例（2026-10-30 实机归档）：** 输入目标波形 SIN，旧程序 `returncode=1`、`after_shape=SQU`，而单条长/短正弦指令均得到 SIN。判断：单条命令可用，连续配置仍未达到目标，排查顺序和完成等待。修正后验收为三组 `returncode=0`、`after_shape=SIN`；幅度依次为 2、1、2 Vpp，输出状态前后依次保持 0、1、1。原始字符串与状态见 [旧失败](evidence/old-reproduction.json) 和 [修复记录](evidence/candidate-hardware.json)，纠正过程见 [C1](collaboration.md#c1)。

## S2 三台仪器整轮刷新

~~~text
任务：检查多仪器刷新调度，保留现有整轮一致性。
设备清单：[参与同轮刷新的设备]。
输入：[调度器、设备读取、界面时间与高亮相关源码；LabMate 对应 polling.py、instruments.py、panel.py、server.py、app.js]。
轮询周期：[值]；单轮各设备耗时：[样本]。
事件：[外部参数变化、控制完成、读数过程中到达的变化、过期/恢复]。

请先分析事件检测、单台读取、整轮完成和界面呈现的职责。
必须保留：
- 任一仪器参数改变后，清单中的全部设备都刷新。
- 单台新参数读到后及时可见，并保留绿色变化高亮。
- 全部设备卡片与底部共用整轮完成时间及轮次；LabMate 字段为 round_age 和 round_revision。
- 单台数据年龄独立用于 stale 判定。
- 忙时事件不丢失，突发事件可合并；慢读结束后按完成时刻再计周期。
请用模拟时钟覆盖：完成后计时、忙时事件、读取中事件、慢读、控制完成事件。
输出：最小改动、事件时序表、每项检查结果，以及仍需界面观察的项目。
~~~

在 `labmate/` 根目录运行 `python -B skill/run_checks.py --project-root . --only refresh`，调用已有 5 项调度测试。界面观察同时核对新参数、高亮、三卡和底部时间、单台过期及恢复，避免只检查底部倒计时。

**S2 已填示例（模拟时钟）：** 输入一轮在 100.0 秒开始、101.2 秒完成，周期为 3 秒。判断：下次周期刷新应从完成时刻计时。验收为 104.19 秒 `reason()` 返回空，104.2 秒返回 `periodic`。源自 [test_refresh_legacy.py](../sim/historical/file_b19f499ecdf0/test_refresh_legacy.py) 的 `test_three_seconds_after_finished_not_started`；界面高亮和时间一致性另按上述界面步骤核对。

## S3 受限内存下的模型调度

~~~text
任务：检查语音、视觉、指导书处理的资源交接。
硬件内存：[值]；交换空间：[值]；进程及 RSS/可用内存：[采样]。
模式：[active、desired、ready、switching]。
占用标志：[resource_busy、guide_busy]。
相关代码：[asr_engine.py、voice.py、model_runtime.py、guide_resources.py]。
失败记录：[长录音、加载失败、取消、文档处理异常与恢复失败]。

请先区分：暂停计算、停止采集、卸载模型、释放所属进程组。
按录音/识别/模式切换/指导书处理列状态转移表：
- 谁取得资源、何时等待、何时释放；
- 哪个锁保护哪个状态，避免锁顺序倒置；
- 加载失败后仍保留哪个真实 active 状态；
- 每条成功、异常和取消路径怎样恢复视觉与可用操作；
- 内存不足时怎样拒绝新任务，恢复失败怎样保留重试状态。
当前默认引擎与切换策略：[填写本工程现状]。保留现有选择方式，核对按需加载和切回释放。
录音上限与采集完成必须共同核对，覆盖到时停录但音频数据未收满的情况。
输出：状态表、最小修改、故障注入检查计划、实测内存与延迟表。
~~~

历史观察见 model-checkpoints.json 与 ds-integration.json。复用时重新测本机峰值；常驻收益、采集保护和内存保护分别记录，不把存储空间释放量当作运行内存收益。在 `labmate/` 根目录运行 `python -B skill/verify_evidence.py` 可检查历史记录的完整性与检查点数。

## S4 实验回执归属与异步结果隔离

~~~text
任务：根据实际回执生成本轮实验总结。
当前 workflow：[包含 run_id、步骤和完成状态]。
作业记录：[包含操作类型 name、workflow_run、state、result.verified、证据、错误]。
当前仪器设置：[独立快照]。
已有总结：[summary.id、summary.state；轮次标识在 workflow.run_id]。
异步顺序：[请求发出、重开实验、响应到达的时间线]。

请先按 workflow.run_id == job.workflow_run 筛选本轮作业。
保留本轮作业的成功/失败状态；仅 state 为 succeeded 且 result.verified 为 true 的回执可作为已执行依据，再按操作类型区分测量与设置；
测量依据只引用测量操作的实际回读，设置操作回执单列为已确认设置，设置快照列为当前设置。
失败作业保留错误，缺测量时明确缺少该读数。
完成实验生成 summary.id，同一令牌只启动一个总结任务。
等待和保存时，核对当前 phase 仍为 completed 且 summary.id 与该任务令牌相同。
重开先清除 run_id、started_at 和 summary；下一次开始生成新 run_id，迟到结果不覆盖新实验；重启后仍遵守归属。
输出：证据筛选表、测量回执、设置操作回执、当前设置、失败/缺失项和防重复/迟到响应检查。
~~~

在 `labmate/` 根目录运行 `python -B skill/run_checks.py --project-root . --only receipts`，重跑已有 7 项测试。现场还应核对浏览器实际展示与持久化数据；更新页面版本时检查流程、回执和总结是否仍属于同一轮。

代码对应：`experiment_summary.py` 的 `evidence()` 保留本轮操作及验证状态，失败项不附可信 `after`；`local()` 再按操作类型选取测量或光标读数回执。云端输入的 `operations` 同时保留本轮失败记录，`current_settings` 单列，系统提示限定可引用的证据。异步隔离由 `current(token)` 与 `workspace.py` 的 `save_summary(token, summary)` 检查完成状态和总结令牌实现；并非检查 `summary.run_id`。`verified=true` 具体能证明什么仍取决于操作类型和回读内容。

**S4 已填示例（模拟回执）：** 当前设置为 2000 Hz；作业中包含本轮已验证的频率测量 1000 Hz、旧轮作业和本轮失败作业。判断：旧轮排除，本轮失败保留状态但不携带可信测量，设置单列。验收为送入总结的 `operations` 共 2 项，失败项没有 `after`，并保留 `current_settings`；另一个云端失败且无测量回执的测试，要求本地总结提示缺少已核对回执且不把 2000 当测量值。源自 [test_experiment_summary.py](../sim/historical/file_b19f499ecdf0/test_experiment_summary.py) 中 `test_verified_run_evidence_and_settings_separated`、`test_cloud_failure_preserves_honest_local_result`。

## S5 DS 转发启动就绪与断线重连

~~~text
任务：检查后台转发的启动、就绪、重连与停止。
进程清单：[名称、PID、命令行，不含凭据]。
计划任务：[运行状态、目标 runner]。
当前日志：[本次 START PID、UART relay ready、RECONNECT、EXIT]。
停止标记：[存在/不存在]。
相关代码：[run_cloud.py、start-background.ps1、start-cloud.ps1]。

请先构造就绪判定：
1. 正好一个预期 pythonw 后台 runner，任务处于运行状态，目标路径匹配。
2. 日志 START 对应当前 PID。
3. 最近的重连之后已出现 UART relay ready，随后没有 EXIT。
4. 没有人工停止请求。
再检查失败后延迟重连、启动时板卡未就绪、等待中停止及不重复启动。
网络/串口恢复只恢复连接；先前失败请求由用户重新发起。
输出：故障定位、就绪判定、重连/停止时序和模拟检查结果。
本轮使用替身和日志分析，不执行后台启停脚本主体、不打开真实串口。
~~~

在 `labmate/` 根目录运行 `python -B skill/run_checks.py --project-root . --only relay`，调用已有 4 项重连测试和 11 项就绪案例。现场维护继续使用工程已有启停入口，先确认端口占用、正常停止并等待释放，维护后恢复单个进程并核对当前启动段。

**S5 已填示例（模拟进程与日志）：** 当前进程为 `pythonw.exe`、PID 123，任务目标与预期 runner 一致，日志中 `START ... pid=123` 后有 `UART relay ready`，无停止请求，判定就绪。把日志 PID 改为 999，或在 ready 后追加 `RECONNECT waiting`，应判未就绪。源自 [test_relay_startup.ps1](../sim/test_relay_startup.ps1) 的 `ready`、`stale log`、`lost connection` 案例。
